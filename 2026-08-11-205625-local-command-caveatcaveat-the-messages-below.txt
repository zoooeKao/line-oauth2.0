     LINE Messaging API — Push Message (single recipient, text-only)

     Context

     專案 line-oauth-poc 目前只做完 LINE Login + friendship
     檢查，會把使用者是否追蹤官方帳號寫進
     User.officialAccountFollowed，但還沒有能力主動發訊息給使用者。

     這次要串接 LINE Messaging API 的 push endpoint（https://developers.line.biz
     /en/reference/messaging-api/#send-push-message），讓管理者可以透過後端 API
     指定某位已登入過本系統的 LINE 使用者，把一段文字訊息推到對方的 LINE。

     範圍已跟使用者確認：
     - 觸發方式：管理者呼叫 REST endpoint
     手動指定收件人（不是使用者發給自己、也不是登入時自動發）
     - 訊息型別：第一版只支援 text
     - 未追蹤 OA 的處理：後端先擋，回 409 並附上 oaAddFriendUrl，省一次對 LINE
     的 API 呼叫也省配額（本題未直接回答，採推薦預設，實作時如要改為「直接送、由
     LINE 回 403 再轉」也很好改）

     Approach

     在 com.poc.lineauth 新增 messaging package，內含 controller / service /
     client / DTO，全部沿用現有 LineOAuthClient 的 RestClient
     同步呼叫模式。認證直接吃現有 JwtAuthFilter + SecurityConfig（/api/auth/**
     以外都需要 JWT，/api/messages/** 自動被保護）。

     流程：POST /api/messages/push → MessagingController →
     MessagingService（UserRepository.findByLineUserId → 檢查
     isOfficialAccountFollowed()）→ LineMessagingClient.pushText(...) → 回
     {status, requestId}。

     錯誤處理刻意留在 controller 內用兩個 @ExceptionHandler，不引入全域
     @ControllerAdvice，維持 POC 精簡。

     endpoint，無需改設定

     LINE API contract 摘要

     - POST https://api.line.me/v2/bot/message/push
     - Header：Authorization: Bearer {long-lived channel access token} +
     Content-Type: application/json
     - Body：{"to":"U...", 
     "messages":[{"type":"text","text":"..."}]}（訊息陣列最多 5 則，本版只送 1
     則）
     - 成功：HTTP 200，body {}，重點在 response header
     X-Line-Request-Id（UUID，寫進我們的 response）
     - 上游錯誤對應：

     | 上游 | 涵義                                        | 我們回
         |
     |------|---------------------------------------------|---------------------
     -----|
     | 400  | payload 或 userId 不合法                    | 400
         |
     | 401  | channel access token 錯（伺服器端設定問題） | 502（不外洩 401
     給前端） |
     | 403  | 對方未加入 OA / 已封鎖 / 方案不允許         | 409
         |
     | 429  | 配額或速率上限                              | 429
         |
     | 5xx  | LINE 側                                     | 502
         |


     Verification (manual)

     前置：LINE Developers Console → Messaging API 頻道 → 發長期 channel access
     token，寫進 .env；docker compose up --build backend 重啟。

     1. 拿 JWT：走現有 LINE login 流程登入一個已追蹤 OA 的測試帳號，從
     localStorage 或 ?token= 抓 JWT，順便 GET /api/me 拿自己的 lineUserId。
     2. Happy path
     curl -i -X POST http://localhost:8080/api/messages/push \
       -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
       -d "{\"lineUserId\":\"$UID\",\"text\":\"hello from POC\"}"
     2. → 200 {"status":"sent","requestId":"..."}；手機上 LINE 應收到訊息。
     3. 409 未追蹤：docker compose exec postgres psql -U $POSTGRES_USER -d 
     $POSTGRES_DB -c "UPDATE users SET official_account_followed=false WHERE 
     line_user_id='$UID';"，再打一次 curl，應得 409 +
     oaAddFriendUrl。測完把欄位改回 true。
     4. 404：lineUserId 給一個不存在的 U000...000 → 404。
     5. 驗證失敗：text 給空字串 → 400。
     6. 上游 401：把 .env 的 token 改成亂碼重啟 backend，打 happy path 應回
     502，backend log 印 LINE Messaging API returned 401 ...。
     7. 未帶 JWT：不帶 Authorization header → 401（SecurityConfig 已處理）。

     Out of scope（此次不做）

     - 自動測試（POM 目前沒 spring-boot-starter-test，這次不加依賴、不寫 JUnit /
     WireMock）
     - multicast / broadcast / narrowcast
     - 非 text 訊息型別（sticker / image / template / flex）
     - 重試 / 429 backoff / 配額追蹤
     - reply token endpoint
     - follow / unfollow webhook 接收器（可讓 officialAccountFollowed
     即時同步；目前只有在登入時更新）
     - 全域 @ControllerAdvice、共用 RestClient bean

⏺ 為什麼設計成這樣

  - LINE 
  是事實真相：使用者手機上的追蹤狀態隨時可能變（封鎖、解除、重新加），backend
  沒有其他管道知道，只有登入時能問一次
  - DB 只是快取：因為每次 push 都去問 LINE 太慢也浪費 API 額度，所以登入時
  snapshot 一份存 DB，之後 MessagingService 直接讀
  - 副作用：中間如果使用者解除追蹤了，backend 不知道 → push 出去會被 LINE 打回
  403 → 這時 LineApiException handler 會再幫你轉成
  409（這就是計畫裡「第二道防線」的意思）

  想解決「不重登也能即時感知」只有一個正解：接 LINE 的 follow/unfollow 
  webhook，這已經在計畫的 out-of-scope 裡列出來當未來加分項。

  Spring 的請求處理是有先後順序的：

  mermaid
  flowchart LR
      A[Request] --> B[Security<br/>Filter Chain]
      B -- "認證失敗" --> Z1[401<br/>Content-Length: 0]
      B -- "認證通過" --> C[DispatcherServlet<br/>路由到 controller]
      C --> D[@Valid 驗證<br/>PushMessageRequest]
      D -- "驗證失敗" --> Z2[400 Bad Request]
      D -- "驗證通過" --> E[MessagingService]
      E -- "user 不存在" --> Z3[404]
      E -- "未追蹤" --> Z4[409]
      E --> F[LineMessagingClient]
      F -- "LINE 4xx/5xx" --> Z5[502/409/429/...]
      F --> Z6[200 sent]

  你現在卡在最左邊那格（Security Filter Chain 沒過），所以：
  - @Valid 檢查空字串 → 沒跑
  - MessagingService 找 user → 沒跑
  - 訊息送出去 → 沒跑

  不管你把 body 的 text 給 ""、給表情符號、給 5001 字，只要 JWT
  過不了認證，永遠都是 401 Content-Length: 0。
